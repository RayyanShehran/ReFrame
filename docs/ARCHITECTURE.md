# Architecture

## Implemented app flow

The Next.js frontend checks FastAPI `/health` and lets a user inspect/select a full TikTok reference, create a named local project, upload a validated original clip and additional footage, and reopen/delete saved projects. The project UUID in the query string restores server state after refresh; navigation aborts and invalidates pending client work. Reference metadata is a saved snapshot. The backend revalidates and inspects the reference at project creation through the existing official oEmbed service; reopen never contacts TikTok. The reference API keeps its 10-second deadline and 256 KiB streamed response limit.

The shared clip staging context bounds the raw multipart body before parsing (101 MiB), enforces the separate 100 MiB file limit, 120-second duration and 4096-pixel dimensions, and permits one active upload/inspection per process. It validates MP4/MOV extension, MIME/container and a genuine video stream. Audio is optional. The 30-second operation and 15-second FFprobe deadlines, bounded output, file-only protocol restriction, cancellation/reaping, spool closure and safe error envelope remain. Metadata is not proof of complete decoding or browser playback compatibility.

## Project persistence and consistency

Python 3.12 `sqlite3` stores metadata in ignored `data/reframe.sqlite3`, with schema version 17, foreign keys, UUID IDs, parameter binding and explicit transactions. Earlier supported versions migrate additively while preserving projects, media, analyses, recipes, plans and outputs. Every database connection is created, used and closed on one worker thread. Filesystem/database work runs off the async event loop; cancellation waits for the owned worker before releasing ownership. This app supports one process on loopback, one user, at most 10 projects and 10 footage clips per project (500 MiB total source footage). A process lock serializes conflicting project upload/delete work; a separate shared inspection lock covers both upload endpoints.

Projects store a fixed canonical TikTok URL/string ID, metadata snapshot and UTC inspection timestamp. Clips store display metadata, generated media name, SHA-256, UTC save timestamp and state. Storage names and project IDs are validated before filesystem use; paths are never returned. Runtime data is outside `frontend/public`. Completed outputs and scoped previews use validated project routes; retained inputs are not exposed as arbitrary filesystem paths.

Project uploads use `data/project-staging/`. The lifecycle is staging row, validated metadata/digest row, same-filesystem move to `data/projects/<UUID>/`, then ready transaction. Multipart spools are closed before persistence. The file is flushed before validation. Filesystem moves and SQLite commits are separate operations, so success is returned only after both finish. Failures attempt removal and metadata rollback; unresolved cleanup stays visible. Cancellation after a completed ready commit can leave a valid retained clip, which is discoverable on reopen.

Startup removes generated abandoned staging files, clears staging records, and verifies retained size/digest and metadata. Matching retained bytes from an interrupted validated commit can become ready. Missing/corrupt records become unavailable and expose no clip as ready. Ordinary reads also check file existence/size; digest checking is a startup operation. Valid ready clips are preserved. Unknown schema versions prevent startup. Deletion first persists deleting, removes the project's directory, then deletes its metadata with foreign-key cascade. Failed/interrupted deletion remains visible and retryable; it is never reported successful with retained files remaining. All reconciliation is scoped to ReFrame-owned storage.

The old `POST /api/clips/inspect` remains temporary-only under `data/clip-inspection/`, deletes staged media before returning, and never touches retained projects. The main frontend path uses saved projects.

## Planned processing flow

TikTok reference link → reference media access → reference analysis → Style Blueprint → user settings → Edit Plan → rendering. User-uploaded clips are a separate input to edit planning and rendering. Reference uploads are not a fallback.

Reference analysis produces **observations** about retained source media. Versioned blueprints remain read-only. Saved recipes express creative settings, while a separate saved cut plan turns estimated reference timing into executable footage ranges. Rendering resolves both saved revisions on the server. Later milestones may add other analysis categories or editing. Keeping these boundaries separate prevents analysis data from becoming rendering instructions by accident.

A temporary-only developer CLI under `tools/` and experimental app retrieval share `backend/reference_engine.py`; the API never imports the CLI entry point. The extraction retained the reviewed Windows Job Object/POSIX group containment and CLI regression boundaries. Retained user clips and reference media remain separate, outside `frontend/public`.

## Experimental reference operation lifecycle

`reference_jobs.py` owns one asyncio task for either retrieval or color analysis, with blocking processing in a worker thread and a cooperative stop event. POST starts from the saved canonical identity or retained media, GET reads SQLite status. A short start lock enforces one global expensive owner across both operations and makes duplicate starts idempotent; canceled start requests finish establishing ownership. A ready result is reused and failure retry creates a new UUID. Processing does not hold the project mutation lock, so health and ordinary project reads remain responsive. Shutdown serializes against launch, signals the owner and joins it. Project deletion first closes starts for that project, signals/joins its owner, then cleans staging and deletes files/records. Unconfirmed containment in either operation blocks all new media jobs until manual review.

SQLite stores current operation ID, running/ready/failed state, UTC timestamps, safe failure details, generated filename and validated media metadata. No row represents idle. Media includes digest/size, duration/dimensions/codecs/audio presence, decoded counts, retrieval timestamp and tool versions. The downloader receives no caller-supplied URL or flags, cookies, personal config or geo bypass. Reference media is a generated `.media` file inspected by FFprobe/FFmpeg, avoiding user-upload MIME/filename assumptions.

Staging is under `reference-staging/<operation UUID>`. Processing retains the 50 MiB accepted file, 60 MiB aggregate polled budget (100 ms; possible overshoot), 150-second monotonic deadline, bounded captures, pre-download ID check and nonempty decode checks. Additional checks require finite positive duration ≤120 seconds, real video excluding attached pictures and positive dimensions ≤4096. Each stage is capped by remaining time. Post-processing hashing/retention is also deadline checked; confirmed process termination and cleanup can take longer.

Commit records candidate metadata, moves the file to `projects/<project UUID>/reference-<operation UUID hex>.media`, removes staging, rechecks active project/current running operation, then commits ready. Filesystem/SQLite are not atomic: failure removes only this attempt's generated destination and records a safe failed state; late workers cannot revive projects or replace newer attempts. Restart changes running to failed/interrupted, removes unfinished retained files and owned staging without retry, and validates ready size/digest. Unconfirmed termination records `cleanup_safe = 0`, preserves quarantine across restart and blocks retry/deletion for manual review. Cleanup failures are never silently marked ready or deleted. Normal shutdown joins owned processing; forcibly killing the backend, disk failure and intentionally escaping POSIX groups remain limitations.

The UI separates reference media from user footage. A shared operation hook restores retrieval/color state, polls every 2 seconds for at most 3 minutes with 10-second request limits, supports explicit failure retry, and invalidates requests on navigation without canceling server work. Saved recipes now support color-only rendering, native playback and downloads; render polling allows six minutes.

## Offline persisted color analysis

`color_analysis.py` reuses `reference_engine.run_command` and the reviewed Windows Job Object/POSIX group containment. No extractor or network call is involved. Typed POST/GET `/api/projects/{UUID}/style-blueprint` expose idle/running/ready/failed operations; no row is idle. `color_operations` holds the current UUID, source hash, algorithm version, timestamps, safe failure/cleanup state and complete JSON result. The [blueprint schema](STYLE_BLUEPRINT.schema.json) is generated from the validated Pydantic model; component schema version 1 differs from database version 4. Algorithm version is `encoded-rgb-midpoints-v1`.

Start, ready status and recovery validate source existence, size and SHA-256. Pipeline verifies the digest before and after decoding; commit rechecks the retained reference operation, digest, active project, current running analysis UUID, algorithm and stop/deadline. Confirmed process completion and staging deletion precede a single ready/result transaction. There is no separate result file or partial ready record. Canceled, deleted or superseded workers cannot commit. Failure clears any blueprint. Interrupted recovery does not restart jobs; generated UUID staging is removed only when cleanup is confirmed safe. Unknown staging names are left alone. External concurrent edits after a hash check are outside transaction isolation; the next status read detects changed bytes. Ready status hashing has a 10-second cap and runs off the event loop, while ordinary project reads remain lightweight.

Sampling uses the first non-attached video stream, its positive finite duration (format duration only if unavailable), and 12 targets `(i + 0.5) * duration / 12`. PTS is normalized and shifted by half an interval before FFmpeg `fps` nearest rounding, start_time=0 and eof_action=pass. Frames are area-resized to 96 × 96 without padding or autorotation and converted to RGB24, with one decode/filter thread. Exactly 12 frames / 331,776 bytes are required. Short clips duplicate source frames; target timestamps are requested positions rather than promises of distinct frames. Frame timing and decoder versions can affect values. See official [FFmpeg filter documentation](https://ffmpeg.org/ffmpeg-filters.html) and [FFprobe documentation](https://ffmpeg.org/ffprobe.html).

All resized pixels/time samples receive equal weight. Normalized channel means divide by pixel count × 255. Encoded brightness uses `(0.2126R + 0.7152G + 0.0722B)/255`; percentiles interpolate at `(N-1)*p`, with contrast p95−p05. HSV saturation is `(max−min)/max`, black zero, averaged over pixels. Palette uses channel bins of width 32, top five counts descending and lexicographic bin tie-breaking; each bin representative is its mean RGB rounded half up. Counts divide by all sampled pixels; explicit displayed coverage is their sum, possibly below one. Model validation enforces finite normalized units, ordered percentiles, contrast/coverage consistency and the 12 midpoint/count/byte invariants.

Color metadata is inspected before RGB sampling. Supported primaries are BT.709; transfers BT.709/sRGB/gamma22; matrices BT.709/RGB; ranges limited/full. Other tags and HDR side metadata are rejected, including PQ/HLG, BT.2020/P3 and mastering/content-light/Dolby metadata. Missing tags produce a visible SDR warning; missing YCbCr matrix/range explicitly uses BT.709/limited. Untagged HDR cannot reliably be detected. No tone mapping, physical exposure, camera-setting, LUT or temperature inference occurs. Pacing/transitions/captions/audio are `not_analyzed`.

Bounds preserve ≤50 MiB retained media, ≤120 seconds and dimensions ≤4096. Color processing has a 120-second monotonic deadline; version commands ≤5 seconds each, probe ≤10 and sampling ≤60, capped by remaining time. Hash verification outside processing has ≤10 seconds. Stdout limits are 8 KiB/version, 64 KiB/probe and exactly 331,776 bytes/RGB; stderr readback ≤64 KiB. The shared 100 ms watchdog applies a 2 MiB color staging budget, with polling/termination overshoot rather than a filesystem quota. Cleanup/joins may exceed the processing deadline. Forced backend termination and deliberate POSIX group escape remain limitations. Measurements, palette, target/sample coverage, versions, warnings and limits are read-only in the UI; blueprint editing/semantic matching/image mode remain unimplemented; saved planning and rendering are separate.

## Independent estimated pacing component

`pacing_analysis.py` binds the existing analysis persistence/commit/recovery functions to `pacing_operations` and `pacing-staging`; `reference_jobs` routes the same lifecycle owner to its pipeline. The new table is additive in database version 4. Color schema/data remain version 1, unchanged. Typed POST/GET `/api/projects/{UUID}/pacing` use the same operation envelope with a separate validated [pacing blueprint version 1](PACING_BLUEPRINT.schema.json), algorithm `scdet-consecutive-v1`. No automatic acquisition or analysis occurs. Pacing failure clears only its result. All analyses/retrieval share one expensive worker; quarantine in any table blocks new work. Deletion cleans both analysis components after joining the owner. Source hashes and reference operation identity are rechecked using the existing path; ready reuse, atomic publication, interrupted recovery and stale/canceled/deleted rejection retain the color guarantees.

The shared bounded metadata inspection selects genuine video, duration/dimensions and SDR assumptions. Pacing normalizes PTS, area-resizes to maximum dimension 320 and even dimensions ≥2 (preserving aspect within rounding), converts to YUV420P, clears incoming frame metadata, and runs `scdet=threshold=10:sc_pass=0` followed by metadata print to bounded stdout. Every decoded frame is analyzed; no fps/select/color-sample reuse. The parser requires contiguous numbered frame records, finite monotonic normalized times, numeric score/MAFD in [0,100] and valid detector time aligned within 2 ms of frame PTS. Successful EOF decoding and complete nonempty metadata are required. Candidate times use frame PTS, sorted/unique and strictly interior. More than 1,000 raw candidates fails, even if deduplication would reduce them. Shots partition [0,duration]; the model validates intervals, count, arithmetic mean, median and cuts/minute consistency.

Bounds: 120-second overall deadline, versions 5 seconds each, probe 10, detector 90, all capped by remaining time; 1 MiB detector stdout and the inherited 2 MiB/100 ms staging watchdog, with honest overshoot and explicit bound failure. Tool output is not a partial result. Existing media/digest/capture/containment limits remain. Schema records source/tool/algorithm versions, threshold, dimensions, successful frame count, candidates, intervals, statistics and interpretation limits. Pacing estimates do not identify transition types; flashes/motion and similar shots limit accuracy. Transitions/captions/audio remain `not_analyzed`. The existing client hook independently restores color and pacing; an expandable accessible shot table bounds screen space without hiding stored intervals. Official [scdet](https://ffmpeg.org/ffmpeg-filters.html#scdet) and [metadata](https://ffmpeg.org/ffmpeg-filters.html#metadata_002c-ametadata) documentation define the detector and output keys.

## Saved footage color (Milestone 9)

POST/GET `/api/projects/{UUID}/footage-color` uses the existing lifecycle owner, slot, polling, 120-second overall deadline, process containment, bounded tool output and 2 MiB polled staging budget. No retrieval occurs. A source-specific hash helper accepts footage up to 100 MiB; its default remains the reference's 50 MiB. Processing and SDR policy are unchanged (`encoded-rgb-midpoints-v1`, 12 midpoint 96×96 RGB samples, 331,776 decoded bytes).

SQLite version 5 additively creates `footage_color_operations`, preserving reference color/pacing, clips and earlier results. Footage blueprint schema 1 ([schema](FOOTAGE_COLOR.schema.json)) reuses the color structure with its own project UUID, generated clip ID and SHA-256 identity. Source, hash and algorithm are checked at start, before/after decode, commit, ready reads and recovery. Missing/changed footage invalidates only its result. Failure requires explicit retry; interrupted recovery, deletion joins, quarantine and stale-operation checks use the existing implementation. Existing projects are analyzed only on explicit action.

Comparison is derived in the browser from two valid color results; it is not persisted or a grade. All normalized differences are `(reference - footage) × 100` percentage points. Results are revalidated on restoration; completed displays are snapshots until reopening/refresh, so external filesystem edits are not continuously watched. Twelve samples can miss brief events; ordinary SDR assumptions and untagged-HDR limitations apply equally to both sources. The app remains single-user/single-process.

## Editable color recipe (Milestone 10)

SQLite schema **6** additively creates `color_recipes` with a project foreign key/cascading deletion, revision, ready/stale state, recipe JSON and safe stale reason. It preserves schema-5 projects, media and analyses. Recipe schema **1** ([JSON schema](COLOR_RECIPE.schema.json)), suggestion algorithm `sampled-color-ratios-v1`, stores both source identities/hashes, analysis schema/algorithm/operation IDs and analysis dates, suggested and selected values, suggested/default strength 0.5, selected strength, explanations, revision and created/generated/updated dates. Measurements are never rewritten by recipe generate/save operations.

Typed project routes: **GET** `/api/projects/{UUID}/color-recipe`; **POST** `/color-recipe/generate` with `{expected_revision: 0}` initially, or `{expected_revision: N, replace: true}` for explicit regeneration; **POST** `/color-recipe` with `{expected_revision: N, selected: {brightness, contrast, saturation}, strength}`. Extra/untrusted fields and nonfinite, boolean, string or out-of-range numeric inputs are rejected with the existing safe 422 envelope. JSON strength is normalized 0…1. Revision conflicts/repeated generation without replacement return safe 409 errors. Revisions increment on each successful generate/save; stale detection preserves revision and setting timestamps. Regeneration preserves original creation date but resets selected values/strength and updates generation/update dates.

Generate/save/read-ready run under the existing project lock, with separate owned SQLite connections and transaction-level revision checks. Generation obtains validated analyses on the server, including bounded source-hash checks; no network, subprocess, decode or new worker is introduced. Read-ready compares source identity/hash, analysis schema/algorithm/operation/date and suggestion version. Missing/changed sources or incompatible analyses persist stale state, retain settings and return **no effective values**. Staleness is sticky even if sources later recover: explicit regeneration is required. Rendering uses a fresh ready read, never raw stored recipe JSON. Completed UI displays are snapshots until refresh/reload or a validated mutation; external disk changes are not continuously watched. This remains a single-process local application.

Deterministic suggestions: brightness `clamp(reference.p50 − footage.p50, −0.10, +0.10)`; contrast and saturation `clamp(reference / footage, 0.8, 1.2)`, using 1 when the footage denominator is strictly below 0.02 and recording insufficient-variation notes. Selected brightness is bounded to ±0.20, multipliers to 0.5…1.5. Effective values are `strength × brightness`, `1 + strength × (contrast − 1)` and `1 + strength × (saturation − 1)`. They describe creative settings, not exposure stops, recovered LUTs, inferred white balance or a match guarantee. The original recipe milestone defined no preview/render; the following section specifies the later renderer.


## Color-only rendering

Database schema **7** additively stores `render_operations` (latest attempt/spec/cleanup state) and `render_outputs` (one completed output), preserving all measured analyses and recipes. Spec schema 1 / renderer `sdr-eq-mp4-v2` snapshots the server-validated recipe revision, exact effective values, both source identities/hashes and analysis bindings, and fixed encoder/output settings. Clients send only an expected revision; mismatched revisions and stale recipes fail safely. Identical running/ready specs reuse work. Rendering extends the existing shared slot, containment, cancellation, deletion, quarantine and recovery dispatch; it does not introduce a job framework.

The first non-attached video and first audio stream are used. FFmpeg applies display autorotation, normalizes video PTS to zero, area-scales the displayed dimensions, converts full/limited source range to limited BT.709 YCbCr, makes square pixels, selects yuv420p, applies **eq brightness/contrast/saturation**, then samples at **30 fps with nearest rounding**. Gamma stays neutral. The recipe already interpolated strength; the renderer never multiplies it again. Missing YCbCr matrix/range explicitly assumes BT.709/limited. Ordinary BT.709/sRGB/gamma22 transfers are retained (missing transfer assumed BT.709); unsupported HDR/wide-gamut is rejected without tone mapping. RGB averages do not imply white balance. Suggestions may clip colors or differ from sampled RGB intuition: eq operates on encoded YCbCr, not physical exposure.

Compute displayed width from coded width × SAR, then account for orthogonal rotation; fit landscape 1280 × 720 or portrait 720 × 1280 using `min(1, fit ratios)`. Round dimensions down to even numbers, allowing less than two pixels of aspect-rounding error; no crop or pad. Nonorthogonal rotation or invalid metadata fails explicitly. MP4 uses libx264 CRF 20/veryfast, yuv420p and faststart. CFR 30 may repeat/drop frames; it does not preserve source frame cadence. Video duration must agree within **2/30 seconds**. Audio retains its offset relative to video, trims pre-video samples, uses first-stream AAC at 48 kHz/128 kbit/s and can end early; there is no `-shortest`. Video duration caps the output. AAC decoded duration may differ from stream metadata by at most **2 × 1024/48000 seconds**, with container/audio end allowance 0.1 seconds. Silent input maps no audio.

Processing uses one **300-second monotonic deadline**, including hashes and capped stages (version ≤5 seconds, probes ≤10). Encode and entire-file decode share remaining time. Accepted output is **≤100 MiB**; FFmpeg's file-size stop is followed by explicit size and decode validation. The shared **100 ms** aggregate staging watchdog has a **120 MiB** budget for output, partials and logs. Polling/termination can overshoot; this is not a filesystem quota. Stdout caps: 8 KiB/version, 64 KiB/probe and 2 MiB/full decoded framehash; stderr readback ≤64 KiB. Logs exceeding bounds fail, never produce a partial ready result. Cleanup/containment joins may exceed the processing deadline.

Before publication, verify codec/pixel format, expected dimensions/SAR/frame rate/audio presence/duration, then decode **the entire output** to raw video and PCM framehash packets with FFmpeg `-xerror`. Require actual nonempty video frames and audio samples when present, consistent decoded counts/durations, bounded output size and SHA-256. Recheck both source hashes, analysis identities/versions, current running UUID, active project and stop/deadline. Under the existing project lock, atomically move the validated candidate to its generated destination, remove staging, and atomically save ready metadata. Remove the previous completed file only after the replacement transaction succeeds; cleanup failure restores its metadata and explicitly fails the replacement. Startup removes generated unreferenced outputs and confirmed-safe UUID staging; unfinished work becomes failed, never automatically retries. Uncertain containment retains staging and blocks new jobs. SQLite/file changes are not a cross-filesystem transaction; forced termination and external edits after validation remain limitations, with startup reconciliation for generated orphans.

Recipe edits do not mutate an in-flight spec. A completed older revision stays explicitly **outdated**, while changed/missing sources prevent valid-current publication. Inline/download routes validate project/output ownership and the completed file's SHA-256, then use installed Starlette `FileResponse` with native Range handling (200/206/416). The project lock spans validation and file response to prevent replacement/deletion races; a slow local download can delay other project operations. Historical outdated outputs can be served with explicit revision/outdated headers; replaced/deleted output IDs cannot resolve. This remains one local process without cross-process coordination.

Official references checked for this implementation: [FFmpeg eq/scale/fps](https://ffmpeg.org/ffmpeg-filters.html), [FFmpeg timestamp/rotation options](https://ffmpeg.org/ffmpeg.html), [decoded framehash format and faststart](https://ffmpeg.org/ffmpeg-formats.html), and the installed Starlette `responses.py` file-response/range implementation.

Renderer v2 makes the BT.709 input matrix explicit and keeps audio offsets relative to video. Earlier v1 outputs remain readable and are labeled outdated; upgrading does not silently rerender or overwrite them.


## Reference-paced cut planning and rendering

SQLite version **8** additively creates `edit_plans`, preserving all earlier projects, analyses, recipes and outputs. [Plan schema 1](EDIT_PLAN.schema.json), generation algorithm `reference-timing-grid-v1`, stores reference source hash and pacing operation/schema/algorithm/date binding, footage identity/hash, 30 fps, requested duration, available footage frames, total output frames, ordered half-open source/output frame ranges, suggested starts, sub-frame merge count, revision and UTC creation/generation/update dates. Recipe revisions are deliberately absent from this independent plan. Missing/changed sources, changed pacing identity/version or incompatible generation versions mark it sticky stale without deleting ranges. Generation requires a valid saved recipe; plan inspection/save otherwise depends only on its timing sources.

Typed GET `/api/projects/{UUID}/edit-plan`; POST `/edit-plan/generate` accepts expected_revision, optional finite positive output_duration_seconds and explicit replace=true for regeneration; POST `/edit-plan` accepts expected_revision and source_starts_seconds only. The server reads validated pacing, footage identity/hash and recipe. It caps duration at min(reference, footage), rejects durations below one frame and increments revisions under the existing project lock and transaction. Extra source/target fields, nonfinite/boolean/string starts, overlap, wrong counts, out-of-bounds ranges and stale saves are rejected. Revision conflicts retain client drafts until explicit reload; regeneration replaces saved edits; Reset changes only the local draft until saved. Neither operation changes measured analyses.

Generation walks ordered shot lengths to the requested duration and trims the last. Intervals shorter than 1/30 second merge into their predecessor; initial sub-frame intervals join the next, or one group if all are short. Total output and available footage frames floor decimal seconds times 30. Cumulative boundaries round half up, capped at the floored output end; duplicate boundaries merge rather than emit zero lengths. More than **60 resulting segments** is an explicit plan_too_complex failure. For output starts O_i, unused frames U and N>1, suggested source start is O_i + floor(i*U/(N-1)); internal gaps differ by at most one frame, first start is zero and last end fits the footage grid. For one segment, start=floor(U/2). User starts round half up to the same grid; target lengths remain fixed. Continuous selected ranges receive a visible warning: boundaries alone create no jumps. Estimated pacing retains detector limitations; no semantic selection occurs.

Render POST adds optional expected_plan_revision to the existing expected_revision for recipe. Missing plan revision selects the unchanged whole-clip `sdr-eq-mp4-v2` renderer. Cuts use `sdr-eq-mp4-v3`; the backward-compatible specification schema 1 gains an optional full edit_plan snapshot (older JSON defaults to null). This binds exact ranges, provenance and both saved revisions. Current plan/recipe edits mark completed outputs outdated without destroying playback. Publication rechecks source hashes and pacing binding, current operation/project and deadline; an edit during processing may publish its older bound revision explicitly outdated, while changed sources or deleted/stale operations cannot publish. GET and video headers include recipe and optional cut-plan revisions. There is one shared render worker and one latest completed output per project.

Cuts normalize source video PTS, apply the existing aspect/range resize, resample to 30 fps, select frame numbers inside the validated chronological half-open ranges and concatenate by `setpts=N/(30*TB)`. This streaming selection is equivalent to ordered trim/concatenation without sixty buffering video branches. Effective `eq` color settings apply **once after selection**. Audio normalizes against video start, resamples to 48 kHz with `async=1:first_pts=0`, uses bounded `apad=whole_len=footage_frames*1600` and trims to that total. Each selected range then trims exact sample indices frame*1600, resets PTS and concatenates. Missing initial/internal/tail audio timestamps are padded; absent audio creates no stream. Hard audio cuts may click; AAC padding and lossy encoding remain limitations. See official [select, trim, PTS and concat filters](https://ffmpeg.org/ffmpeg-filters.html) and [resampling timestamp policy](https://ffmpeg.org/ffmpeg-resampler.html).

The server-generated filter graph is capped at **16 KiB**, with at most 60 audio branches and no per-segment media files. It uses current `-filter_complex` directly (FFmpeg 9 removed the older script option); the bound keeps the Windows command line small. Existing 300-second overall deadline, 100 MiB output, 120 MiB staging watchdog (100 ms polling with overshoot), bounded capture, containment, quarantine, retry, replacement rollback and deletion/recovery remain. Verification requires exact planned video frame count, complete decoded audio where present, expected output duration/streams and hash before publication. Ordinary SDR and 30 fps conversion can change appearance/repeat or drop frames; no transitions, captions or matching guarantee is introduced. Saved audio modes extend this renderer as described below.

## Saved audio settings and rendering

Database version **9** adds independent `audio_settings` (foreign-key cascade, revision, ready/stale state, settings JSON and safe message), preserving all earlier records. [Audio schema 1](AUDIO_SETTINGS.schema.json) stores original/reference/mix/mute, finite strict volumes 0–100%, reference offset 0–120 seconds, revision and UTC creation/update dates. Reference modes include server-resolved canonical video identity, media SHA-256 and retained retrieval operation UUID. No saved record means original at 100%, revision zero. Settings do not modify analyses, color recipes or cut plans.

Typed GET/POST `/api/projects/{UUID}/audio` returns settings, status and stream availability. POST accepts choices plus `expected_revision` and optional `refresh_sources`. It rejects nonfinite, out-of-range, extra trusted fields, stale revisions, unavailable required streams and offsets at/after the reference video end. Reference requires ready retained audio; Mix also verifies retained footage/audio. Stale settings preserve choices; an explicit **Save with current sources** rebinds the reference after reload. This is an ordinary settings save, not a reuse-rights approval workflow. Original silent inputs remain valid. The UI suggests 70/30 on first Mix selection and 100% on single-source selection, displays missing-stream reasons and blocks rendering unsaved choices.

Render POST binds `expected_audio_revision`. Its versioned specification gains a full audio snapshot; `sdr-eq-mp4-v4` is used after settings are saved. Older specs default to original/revision zero and retain v2 whole/v3 cut compatibility. Old requests lacking audio revision are accepted only at that unchanged default. Audio edits during/after rendering make the bound output outdated, preserving playback/download. Response headers expose `X-Audio-Mode` and `X-Audio-Revision`. Original audio uses existing footage timing/cut sample ranges with explicit gain; Mute uses `-an`, without even a silent stream.

Reference input is probed and hashed within the existing render deadline; the saved identity, hash and retrieval operation must match. Audio PTS subtract the reference **video** start, then `aresample=48000:async=1:first_pts=0` fills/trims timestamps, retaining late audio as initial silence and trimming pre-video audio. `async=1` does not enable automatic stretching. The offset rounds to the nearest 48 kHz sample. `apad=whole_len=offset_samples+output_samples` and exact sample trim produce output-length audio from that normalized offset; reset PTS starts it at output zero. It is continuous across footage cuts, never looped, with shorter tracks padded rather than truncating video. Output sample count rounds duration×48000; cut output uses exact frames×1600.

Mix normalizes both tracks to 48 kHz floating-point stereo, applies saved gains divided by 100 and pads them to output length. `amix=inputs=2:duration=longest:normalize=0:dropout_transition=0` disables automatic gain changes as a source ends. `alimiter=limit=0.95:attack=5:release=50:level=0:latency=1` supplies lookahead limiting, disables automatic level normalization, compensates lookahead delay and flushes remaining samples at EOF. Limiting intentionally reduces loud peaks; stereo conversion and lossy AAC can affect waveform/amplitudes. Reference/mix output is checked for complete decoded PCM and duration within two AAC packets (2048/48000 seconds). Audio presence is selected-mode dependent; reference bindings/audio availability are revalidated again before publication. Inherited worker, containment, staging/capture bounds, stale UUID/deletion protection and compensation are unchanged; there is no second job framework.

Current official method references: [FFmpeg amix/alimiter filters](https://www.ffmpeg.org/ffmpeg-filters.html#amix), [limiter latency/level options](https://www.ffmpeg.org/ffmpeg-filters.html#alimiter), and [resampler timestamp/async behavior](https://ffmpeg.org/ffmpeg-resampler.html). Reference audio may include speech and sound effects. Retrieval does not establish reuse rights. No source separation, music identification, beat detection or audio uploads are implemented. Manual/imported captions extend the renderer below.

## Saved captions and burned-in export

SQLite migration **10** adds one independent `caption_tracks` row per project (foreign-key cascade, revision, ready/stale state, JSON and safe message), preserving all earlier records. The server binds footage UUID/file/hash, whole/cuts mode, output duration and, for cuts, saved plan revision. Color/audio revisions are deliberately absent. Missing/changed footage or changed plan makes the track sticky stale without deleting text. Rebinding requires explicit confirmation and full validation; times are never shifted or truncated.

Typed GET/POST `/api/projects/{UUID}/captions` reads/saves the track. POST accepts choices, expected_revision, mode, expected_plan_revision for cuts, and confirm_rebind; client source fields are rejected. The existing project lock plus transactional revision checks protect saves/deletion. Errors name cue/field constraints without echoing input. Half-open intervals must be finite, ordered, nonoverlapping and within output duration. Bounds: **200 cues / 200 Unicode code points per cue / two explicit lines**. Enabled requires at least one cue. POST `/captions/import` streams a raw UTF-8(-BOM) SRT body capped at **128 KiB**, normalizes CRLF, accepts standard indexed comma-millisecond timestamps and returns parsed preview only. It does not persist a track, spool or retain an uploaded file. Plain text includes literal markup-looking strings; unsupported control characters are rejected. Preview replacement edits the client draft; Save separately validates the selected timeline. Conflicts retain edits until explicit reload.

Render POST additionally binds expected_caption_revision (omission only at unchanged default zero). Specification schema 1 gains the exact track snapshot; older JSON defaults disabled/revision zero. Saved tracks use `sdr-eq-mp4-v5`; earlier renderer versions remain readable. Enabled tracks must match the selected mode/plan and source. Caption changes label prior output outdated while retaining it; binding is checked again before publication. Disabled tracks do not require libass. Enabled rendering checks the `ass` filter with a bounded 5-second/8 KiB capability request and returns a useful missing-libass error. This uses the existing worker, 300-second deadline, output/staging/capture limits, containment, recovery, retry and replacement lifecycle.

Server-generated UTF-8 ASS is capped at **512 KiB**, in owned staging, with actual output PlayRes dimensions and bundled DejaVu Sans **2.37**. Small/medium/large are 3.5/5/7% of output height, black outline max(0.5 px, 0.3% height), no shadow, 4% horizontal and 6% vertical margins; libass may wrap long text into additional visual lines. English/Arabic are verified with complex shaping and bidi Encoding=-1; emoji/CJK and other missing glyphs can show boxes or vary with system fallback. [Bundled font license](../backend/fonts/LICENSE.txt) retains the Bitstream Vera/DejaVu/Arev redistribution notices; font SHA-256 is `7da195a74c55bef988d0d48f9508bd5d849425c1770dba5d7bfc6ce9ed848954`.

Cues use final output time after cuts. At the renderer's 30 fps, first frame at/after each boundary is ceil(seconds*30); ASS centiseconds floor that frame time, preserving exact half-open membership on output frames. Stored seconds are unchanged. A cue entirely between frames has no visible frame. Literal braces use libass's escaped-brace extension, literal backslashes receive an invisible word joiner to prevent ASS newline/spacing escapes, and only authored newline becomes ASS newline. User text is confined to the last event-text field, never commands, paths or filter expressions. Server-owned paths receive both AVOption and filter-graph escaping, including Windows drive colons/apostrophes/brackets/commas/semicolons, verified by a real render. ASS burns **after cuts, scaling, color and frame normalization**, so grade does not tint caption text; audio branches are unchanged. Official references: [FFmpeg ass filter](https://www.ffmpeg.org/ffmpeg-filters.html#ass), [libass literal-brace/bidi extensions](https://github.com/libass/libass/wiki/Libass%27-ASS-Extensions), and [DejaVu licensing](https://github.com/dejavu-fonts/dejavu-fonts/blob/master/LICENSE). No OCR, reference-caption extraction, animation or transition effects. Optional local transcription is described below.

The optional pinned extra is faster-whisper **1.2.1**, CTranslate2 **4.8.2**, ONNX Runtime **1.30.0**, with all transitive versions locked. [SYSTRAN's adapter documentation](https://github.com/SYSTRAN/faster-whisper) describes CPU/int8, local files, VAD and word timestamps. The model is [multilingual base at immutable revision ebe41f70d5b6dfa9166e2c581c45c9c0cfc57b66](https://huggingface.co/Systran/faster-whisper-base/tree/ebe41f70d5b6dfa9166e2c581c45c9c0cfc57b66). Explicit setup downloads only config/model/tokenizer/vocabulary and writes their sizes/SHA-256 in an ignored manifest. Ordinary runs check revision/presence/sizes and trust the local cache; they do not rehash the model on every job. Restore a damaged cache through explicit setup. Auto uses detected language; en/ar force the chosen transcription language, never translation.

FFmpeg extracts the completed export audio, rather than source footage, to mono 16 kHz signed 16-bit PCM. A bounded 10-second/8 KiB FFprobe query validates the video stream start; extraction uses `-copyts` and `asetpts=PTS-(video_start)/TB,aresample=16000:async=1:first_pts=0:min_hard_comp=0.001`. It subtracts the **video** origin rather than audio STARTPTS, pads delayed audio with actual initial silence, trims pre-video samples and fills timestamp gaps (1 ms hard-compensation threshold), without automatic stretching. The output `-t` cap applies after this normalization. See official [timestamp copying](https://ffmpeg.org/ffmpeg.html#Advanced-options) and [resampler filling/trimming and first_pts](https://ffmpeg.org/ffmpeg-resampler.html). Bounds remain: at most **3,840,000 bytes / 120 seconds**. Cue validation uses the completed output's measured duration. Inference runs in an owned Python subprocess under the inherited Windows Job Object/POSIX group containment. Overall **300 seconds**, extraction stage at most 30 seconds, bounded captures (audio tool 8 KiB, inference JSON 512 KiB), aggregate **8 MiB staging** watched every 100 ms. Polling permits overshoot and is not a filesystem quota; stop/cleanup may exceed the processing deadline. Termination must be confirmed before deleting staging; uncertainty remains quarantined, blocks new work and reports cleanup failure. Recovery fails interrupted jobs without rerunning inference. Project deletion, source-hash rechecks and current-operation/active-project checks before publication use the existing worker and lock. No second framework.

Finite, ordered segment/word intervals and nonempty plain text must lie inside output duration. Words preserve model seconds without rounding. At most 20 ms of word overlap is normalized by advancing the later start to the preceding end; larger overlaps, backwards/zero-length intervals and missing word timestamps fail. Cues split at segment boundaries, punctuation, approximately 80 characters or five seconds using word boundaries (one longer valid word remains intact). Bounds remain **200 cues, 200 Unicode code points and two explicit lines**, with at most 10,000 validated input words. Exceeding bounds fails explicitly, never returns a partial proposal. An empty segment list yields a clear empty proposal; a nonempty segment without words is invalid. VAD cannot guarantee correct speech detection, text or alignment, especially with music. Review is required. Rendering continues to use the existing 30 fps half-open interval policy and font limitations. No OCR, diarization, translation or animated highlighting.


## Saved output framing

[Settings schema 1](FRAMING_SETTINGS.schema.json) stores format original/portrait/square/landscape, fit/fill, finite strict horizontal/vertical positions **0–1**, revision and UTC creation/update dates. Absent settings mean Original/Fit/center, revision **0**. `GET /api/projects/{UUID}/framing` restores defaults or saved settings; `POST` accepts choices plus `expected_revision`, checks the current revision inside the transaction and returns 409 on conflict. Publication retains the existing source-hash/current-operation/project/deadline guards. An edit during rendering may publish its bound older settings explicitly outdated. Headers add `X-Framing-Revision` and `X-Output-Format`.

Geometry uses coded width × pixel aspect ratio, coded height and orthogonal display rotation. FFmpeg autorotation is enabled; explicit scale dimensions normalize the resulting display shape and `setsar=1` produces square pixels. Original retains the prior no-upscale fit within 1280 × 720 or 720 × 1280, rounded down to even pixels. Fixed canvases are exactly Portrait **720 × 1280**, Square **720 × 720**, Landscape **1280 × 720**. Fit uses the minimum proportional scale, rounded down to even dimensions, then centered black padding. Fill uses the maximum scale, rounded up to even dimensions, then an even-aligned crop at `position × available movement`, bounded from either edge. Pixel rounding can introduce a small aspect approximation; scale dimensions above **8192** fail explicitly to bound intermediate frames. Nonorthogonal rotation remains unsupported. See official [scale, crop and pad filters](https://ffmpeg.org/ffmpeg-filters.html) and [rotation/autorotation](https://ffmpeg.org/ffmpeg.html#Video-Options).

The pipeline remains normalized source timing → square-pixel scale → saved cuts/color → framing → captions → existing H.264/AAC encoding and full-output validation. Padding is added after color so bars remain black. ASS PlayRes and font size use the final canvas, so source cropping cannot crop captions. Whole/cut audio graphs, duration, 30 fps timing, audio offsets, bounds, owned worker, cancellation, cleanup and replacement are unchanged.

`GET /framing/source` supplies normalized display dimensions and Original dimensions for crop-axis availability, including legacy clips whose upload metadata omits SAR/rotation. It performs a metadata-only FFprobe check under the existing shared slot's start lock and project lock (busy while another media job runs), verifies the retained footage hash with its **100 MiB** limit, and joins on cancellation. It has a **20-second overall / 10-second tool** cap, **64 KiB output**, and the existing owned-process containment and staging watchdog. Safe staging is removed after confirmed termination. Unconfirmed termination or failed deletion explicitly reports cleanup failure, retains inspection staging and blocks new jobs for manual review; startup does not silently remove it. This adds no worker framework and performs no decode or network access.
