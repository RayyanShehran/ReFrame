# Implementation status

## Milestone 1: development foundation

The responsive Next.js shell and FastAPI health endpoint remain in place. Frontend and backend foundation checks run in CI.

## Milestone 2: TikTok reference-access feasibility

ReFrame's intended inputs are a TikTok link for the reference and, separately, uploaded user clips. A corrected developer-only probe under `tools/` retrieved one public TikTok documentation sample on 2026-09-29 and verified 12,288 decoded RGB frame bytes plus 16,000 decoded audio samples. The earlier probe observation remains documented, including its exit-code-only decode limitation. Another canonical sample failed at metadata extraction, and tested short-link fixtures resolved to TikTok's home page. See [the evidence and limits](TIKTOK_REFERENCE_FEASIBILITY.md).

The decision is **proceed experimentally**: local technical feasibility is demonstrated for one link. Production-host reliability, rights and platform permission, and a working fresh short link remain unresolved. The architect will choose any production ingestion approach after reviewing this evidence.

## Milestone 3: reference selection

The app accepts full TikTok video URLs, retrieves public title and creator metadata through TikTok oEmbed, and lets the user select or clear a reference. Short links receive guidance to paste the full URL. Selection is in memory and clears on refresh. This milestone does not retrieve, analyze, or reuse media; a metadata result does not establish access or rights.

## Milestone 4: temporary clip inspection

After reference selection, one user-owned MP4 or MOV clip can be uploaded for technical inspection. Limits are 100 MiB for the file, 101 MiB for the multipart request, 120 seconds, and 4096 pixels per dimension; audio is optional. The endpoint accepts only one file field, permits one inspection at a time per process, and has 30-second request and 15-second FFprobe limits. It returns size, duration, dimensions, codec and audio metadata, then deletes the staged clip. Selection and clip details are in memory; refresh clears them and the clip must be uploaded again when needed. FFprobe is required for clip inspection.

On 2026-09-30, a locally generated 74,889-byte MP4 was inspected through the browser with FFprobe 9.0.2. The app reported 2 seconds, 320 × 240 pixels, MPEG-4 video, AAC audio and 24 fps. The dedicated inspection directory was empty after the response. Generated MP4 and MOV integration fixtures and a corrupt file were also checked with the real tools.

## Milestone 5: persistent local projects

Saved projects now retain one fixed TikTok reference snapshot and one validated user clip. Names are trimmed to 1–80 characters; up to 10 projects are allowed. UUID project URLs restore state after refresh. The backend stores metadata in `data/reframe.sqlite3`, stages uploads separately in `data/project-staging/`, and retains generated media names under `data/projects/<UUID>/`. Runtime data remains ignored and outside the public frontend directory. SHA-256 is computed while streaming. The existing limits and temporary-only inspection API remain unchanged.

The persisted staging/validated/ready lifecycle makes interrupted file/database commits detectable. Startup reconciles owned staging and retained media, verifies digests and marks missing/corrupt media unavailable. Matching retained bytes from an interrupted validated commit can recover to ready. Deletion persists a deleting state and stays retryable after cleanup failure. Conflicting upload/deletion is serialized in this single process. Server workers own separate SQLite connections; cancellation joins worker work before ownership is released. The frontend makes saved metadata snapshots and local retention explicit and confirms deletion by project name.

On 2026-09-30, a browser demonstration created a project, retained the generated 74,889-byte MP4, refreshed, restarted the backend as a new normal process, reopened the same UUID URL and recovered the snapshot and metadata: 2 seconds, 320 × 240, MPEG-4/AAC, 24 fps, SHA-256 `9e8d1ae7ad80d0c8a3217dfea71e022aa8a6a443e8c27ef104613e7fcaee0531`. The retained file was still present after restart. Confirmed deletion returned 204; SQLite then had zero demo project/clip records, its project directory was absent and staging was empty.

Live oEmbed reference inspection succeeded, but the server-side reinspection at project creation was rate-limited (503). The persistence demonstration therefore used an explicitly labeled local reference fixture for creation, with the real upload, FFprobe 9.0.2, SQLite/filesystem, refresh, restart and deletion flow. Reopen after restart used the normal backend and no fixture/upstream call. This does not claim successful live reference creation. Automated tests mock TikTok, use isolated databases/directories and include generated real-media persistence checks.

## Limitations

The app is single-user and loopback-only, with one backend process. It has no cloud storage, authentication, clip replacement, multiple clips, blueprint editing, footage matching, edit planning, rendering or image mode. Reference analysis currently covers color only. Retained clip digest validation happens at startup; ordinary project reads check file presence/size. Color status/start/recovery additionally verify reference hashes. There is no media playback/serving route. Cancellation after a completed clip commit may leave a saved clip; reopen to check before retrying. The developer CLI remains temporary-only. Experimental app retrieval is not a production importer. Health and reference metadata do not require FFprobe. Hard backend termination bypasses graceful join guarantees; unconfirmed process cleanup is quarantined for manual review. A working fresh short-link sample remains unvalidated and short links are not supported in the app.

## Milestone 6: experimental saved reference media

Saved projects can explicitly retrieve their fixed canonical reference into separate local media storage. A single lifecycle-owned task exposes persisted idle/running/ready/failed status with unique operation IDs, UTC timestamps and safe failures. Duplicate starts reuse running operations, another project receives busy, ready media is reused, and failed work needs explicit retry. Shutdown/deletion signal and join owned processing; no network download holds the project lock. Schema version 2 migrates version 1 preserving clips/projects. Startup marks unfinished retrieval interrupted, reconciles retained media and cleans owned staging without automatic downloading. Unconfirmed containment remains quarantined with an explicit cleanup failure.

The shared engine retains reviewed process/resource safeguards and verifies ID, ≤50 MiB file, genuine video, positive finite duration ≤120 seconds, dimensions ≤4096, 12,288 RGB frame bytes and at least one complete PCM sample if audio exists. Audio is optional. The 60 MiB staging watchdog polls every 100 ms and can overshoot; the processing deadline is 150 seconds. Stored metadata includes digest, size, codecs, dimensions, duration, audio presence, decoded counts, retrieval date and versions. The browser polls for at most 3 minutes, supports retry, restores persisted status and leaves server processing running when navigating away. At the Milestone 6 boundary, style analysis was not implemented; Milestone 7 adds color analysis below.

On **2026-09-30 18:22:33 UTC**, one live documentation-sample attempt through the shared engine succeeded on Windows/Python 3.12.14, yt-dlp 2026.8.19 and FFmpeg/FFprobe 9.0.2. The numeric ID matched `6718335390845095173`; 2,004,627 bytes, 10.495011 seconds, 720 × 1280, HEVC/AAC, **12,288 decoded frame bytes and 16,000 audio samples**. SHA-256: `5fa05e7138b9e28ae66b4647e6828287692b91e23d4b3c2afc2ab334d31e5261`. Temporary media was removed. This is live engine evidence, not a claim of a live saved-project/browser workflow; that persistence lifecycle is covered by isolated deterministic tests. Normal project creation still uses real oEmbed without fixture fallback. Earlier Milestone 2/5 observations remain historical evidence.

Local Windows gates passed: **139 backend tests**, Ruff lint/format, **28 frontend tests**, frontend lint/typecheck/production build, and **20 existing spike tests** including both child-containment cases and real timeout handling. New tests cover identity/size/duration/dimensions/cover art/empty decode, optional audio, real generated-media decoding, retention and ready reuse, busy/duplicate/retry, file/database/cleanup compensation, schema-1 migration preserving a clip, interrupted/corrupt-media recovery, deletion/shutdown joins, stale commits, canceled-start ownership, responsive reads and browser polling/navigation/retry. ## Milestone 7: persisted reference color analysis

The retained reference can be analyzed offline through typed project-scoped POST/GET `/api/projects/{UUID}/style-blueprint`. A validated [JSON blueprint schema version 1](STYLE_BLUEPRINT.schema.json), algorithm `encoded-rgb-midpoints-v1`, persists with source identity/hash, versions, 12 midpoint targets/successful samples, decoded byte count, color metadata, warnings, RGB means, encoded brightness percentiles, contrast, saturation and palette. Pacing/transitions/captions/audio remain explicitly `not_analyzed`. Database version 3 adds color operations while preserving older projects, clips and reference records. Completed results are committed atomically after staging cleanup; hash/algorithm changes, missing media and stale/deleted/canceled workers cannot expose a ready result.

The existing lifecycle owner now coordinates retrieval and analysis globally, reuses duplicate starts/ready results, requires explicit retry, joins deletion/shutdown and marks interrupted restart work failed without automatic restart. Uncertain containment preserves staging and blocks all new media jobs pending manual review. The read-only UI restores status after refresh, bounds polling and displays palette, measurements, coverage, assumptions and interpretation limits. Methods and bounds are documented in [README](../README.md#read-only-reference-color-blueprint) and [architecture](ARCHITECTURE.md#offline-persisted-color-analysis).

### Reproducible evidence, 2026-09-30

Real Windows FFmpeg/FFprobe **9.0.2**, Python **3.12.14** processed generated lossless RGB fixtures: pure red/green/blue, gray, black and white matched expected channel means/encoded brightness/saturation; a three-second red→green→blue clip produced 12 midpoint samples, **331,776 RGB bytes**, equal channel means and three one-third palette bins. A single-frame 0.083-second clip produced 12 repeated samples and the missing-tag warning. A real BT.2020/PQ-tagged fixture was rejected as `unsupported_color`. Fixtures are synthetic, not TikTok downloads. Tests also verify deterministic palette coverage/ties and percentile interpolation.

The browser used two explicitly labeled synthetic reference fixtures in isolated storage, with no TikTok call or production project-creation fallback. Analyze reached ready at **19:36:30 UTC**; the changing-color fixture SHA-256 was `1cc03d0cc7b4fbab61b97652fd28a4c59fb12cd6ae74b8362c23b20eaa535d78`. It displayed blue/green/red **33.3% each**, RGB means **33.3% each**, brightness p05/p50/p95 **7.2% / 21.3% / 71.5%** (stored values **0.0722 / 0.2126 / 0.7152**), contrast **64.3%**, saturation **100%**, coverage **100%**, and targets **0.125 through 2.875 seconds in 0.25-second steps**. Refresh restored the same operation `91901113-f8f7-4630-ae9c-eaa82edfe730` and analyzed timestamp. The HDR fixture exposed a safe failure and explicit retry; retry changed operation `0d1e9e13-dcf0-4ded-a96f-8d61a2679643` to `0b93c937-0a48-41a7-9b74-60f98cd97e45` and again rejected the unchanged unsupported input.
